## 0. Решения пользователя (зафиксировано)

| Тема | Решение |
|------|---------|
| Свод | **Одна часть**, цельный список лотов (не «Разработка / Реализация»). |
| Scope лота | **Только** из колонки «Доступ» в Своде: есть **Г** → `global`, иначе `local`. |
| Агент Биржи | Умеет выставлять **все** лоты (global и local) по своим алгоритмам. |
| Секретарь | Через Агента биржи может инициировать выставление **только global**. |
| Витрина | **Только** лоты с **положительным государственным остатком** (`qty_remaining` > 0 у гослота). |
| UX | Гражданин видит витрину **согласно статусу**, выбирает лот → заявка → Агент Биржи + СБ. |
| Подтверждение (канон v3) | **Не** «global=Агент СБ / local=Страж» как главная ось. Ось = **иерархия доступа лота vs активная роль** заявителя и подтверждающего (см. §3.4). |
| Авто-принятие | Если у заявителя **активная роль** соответствует доступу лота → СБ **сразу** подтверждает. |
| Эскалация | Если роль заявителя **ниже** требуемого уровня доступа лота → нужно подтверждение **нужного уровня**. |
| Иерархия СБ | Страж **не** подтверждает лот уровня Судьи; Судья **может** подтвердить лот уровня Стража (выше подтверждает ниже). |
| Экспорт | Нет локального лота в городе → статус **«Экспорт»** **без** названия города. |
| Баланс КВАЗИ / +10% / −10% | **Не трогать** в этой итерации. |

### Что изменилось в v3 относительно v2 (кратко)
- **Главная ось подтверждения** сменилась: было `lot_scope` (global→agent_sb, local→live_guardian); стало **уровень доступа лота ↔ роль** (заявитель / подтверждающий).
- **Витрина** явно: сначала смотрит госостаток > 0, по статусу выбирает лот, потом заявка через агента и СБ.
- Примеры авто-СБ: Страж→лот Стража; Судья→лот Судьи — оба сразу.

Устарело / не использовать:
- «Агент Биржи выставляет только Global» — **нет**: только **Секретарь** ограничен global.
- «Подтверждение = Global→Агент СБ, Local→живой Страж» как **единственное** правило — **заменено** иерархией §3.4 (scope global/local остаётся для перемещения/экспорта, не как единственный ключ confirm).
- «После buy всегда ждать СБ» / «ожидает СБ» для любого global — **нет**; при соответствии роли — сразу.
- Экспорт с городом в UI — **нет**: только «Экспорт».
- `affordable=true` как главный фильтр видимости — **нет**.
- Две части Свода — убрать из публичного контракта.

Связанные старые файлы (перекрываются этим промптом):
- `docs/passport-phase-ad-handoff.md` (биржевая часть устарела)
- `docs/passport-exchange-shelf-export-handoff.md` (экспорт с городом / buy-first / confirm по scope — устарело)

## 1. Свод

### Канон
- Один список лотов: код, единица, цена (КВАЗИ), доступ.
- Нет деления ответа API на `parts.development` + `parts.implementation`.
- Тип лота клиенту/ядру: `lot_scope = global | local` **только** из доступа (Г ∈ доступ → global).
- **Уровень доступа лота** (для СБ) выводится из того же «Доступ»: минимальный/целевой статус в списке доступа (Г < Ст < Сд < М < Айя; Мэр — должность, доступ к М по должности — как в КГПС).

### Что сделать в ядре
1. `GET /svod` → плоский список лотов (например `lots: [...]`): `code`, `unit`, `base_price`, `access` / `access_roles`, `lot_scope`, желательно `access_level` / мин. роль для заявки и confirm.
2. Убрать обязательный split work_kind в публичном JSON.
3. Лоты витрины ≠ отдельный «rates»-контур; не смешивать UX.
4. Парсер эталона: одна таблица → каталог.
5. Обновить `docs/algonism/SVOD.md` / law при необходимости.

### Acceptance (Свод)
- [ ] Нет обязательных двух частей в API.
- [ ] У позиции есть `lot_scope` и однозначный уровень доступа для СБ-иерархии.

## 2. Роли на витрине и в заявках

| Роль (активная) | Витрина / заявка |
|-----------------|------------------|
| Гражданин | Лоты, в чьём доступе есть **Г**, и только с госостатком > 0 |
| Страж | Лоты, доступные Стражу (и ниже по иерархии доступа, если так задано Сводом), госостаток > 0; + local/export по отдельным правилам §4 |
| Судья | То же для уровня Судьи (+ может подтверждать уровень Стража) |
| Мэр / Айя | По доступу Свода и должности (Мэр → позиции с М) |

«Согласно статусу» = фильтр витрины и права заявки по **активной роли** (после принятия роли / ВПН), а не по «хочу купить любой код».

## 3. Агент Биржи и СБ

### 3.1. Секретарь → Агент Биржи
- Инициирует выставление **только global**.
- Local от Секретаря → отказ.

### 3.2. Алгоритм биржи (канон v3) — основной поток

```
Витрина: только лоты с qty_remaining государства > 0
    → пользователь (по статусу) выбирает лот
    → подаёт заявку
    → Агент Биржи проверяет заявку через СБ
    → решение по иерархии доступа (§3.4)
```

### 3.3. Выставление остатка (снабжение)
- Секретарь / агентские поставки: по-прежнему наполняют **государственный остаток** (и local-остаток города там, где канон local это требует).
- Заявка с витрины опирается на уже положительный госостаток; агент не «рисует» витрину из нуля без остатка.

### 3.4. Подтверждение через СБ — иерархия доступа (НОВОЕ ядро канона)

**Идея:** подтверждает не «тип global/local», а **соответствие активной роли уровню доступа лота**.

Уровни (возрастание):  
`Гражданин (Г) < Страж (Ст) < Судья (Сд) < Мэр (М)* < Айя`  
\*Мэр — должность; для лотов с **М** в доступе учитывается должность Мэра по КГПС.

**Правила:**

1. **Авто-подтверждение СБ**, если активная роль заявителя **соответствует** доступу лота  
   (роль ∈ доступа / роль достигает требуемого уровня лота).  
   Примеры:
   - Страж подал заявку на лот, доступный Стражу → **СБ сразу подтверждает**.
   - Судья подал заявку на лот, доступный Судье → **тоже сразу подтверждается**.

2. Если активная роль заявителя **ниже** требуемого уровня лота → сделка **не** авто; нужно **подтверждение нужного уровня** (человек/статус того уровня в контуре СБ).

3. **Иерархия подтверждающих:**
   - Страж **не может** подтвердить то, что доступно **Судье** (выше его уровня).
   - Судья **может** подтвердить то, что доступно **Стражу** (ниже / равный ему контур).
   - Общий дух: **выше по статусу подтверждает ниже; ниже не подтверждает выше**.

4. `lot_scope` (global/local) **сохраняется** для:
   - видимости/экспорта/перемещения между городами;
   - правил Секретаря (только global);  
   но **не** подменяет §3.4 как единственный ключ «кто жмёт confirm».

### Что сделать в ядре
1. Политика Секретарь = только global при снабжении/needs от агента.
2. Витрина: filter `qty_remaining > 0` (гослот).
3. Заявка с витрины → Агент Биржи → проверка СБ по §3.4 (авто или очередь на уровень).
4. Права `security/tasks/:id/confirm`: проверять, что роль подтверждающего ≥ уровня лота; Страж не подтверждает судьины лоты.
5. Не менять формулы КВАЗИ.

### Acceptance (Агент / СБ)
- [ ] Секретарь не выставляет local.
- [ ] Витрина без нулевого госостатка.
- [ ] Страж→лот Стража: авто-confirm СБ.
- [ ] Судья→лот Судьи: авто-confirm СБ.
- [ ] Страж не может confirm лот уровня Судьи.
- [ ] Судья может confirm лот уровня Стража.

## 4. Витрина, остаток, Экспорт

### Госостаток (обязательно на витрине)
- На витрине биржи — **только** лоты с **положительным государственным остатком**.
- Пользователь видит подмножество **согласно статусу** (активная роль vs доступ лота).

### Local / Экспорт
- Если в текущем городе нет локального лота (остаток 0), а перемещение возможно → строка **«Экспорт»** **без** названия города.
- Экспорт не отменяет правило госостатка для «обычных» строк витрины; это отдельный display_status для межгорода.

### Что сделать в ядре
1. Listings: не отдавать гослоты с `qty_remaining <= 0` как доступные к выбору.
2. `display_status: "Экспорт"` без города в подписи.
3. Фильтр по статусу на сервере (и дублировать в Passport).

### Acceptance (витрина)
- [ ] Нулевой госостаток не виден как выбираемый лот.
- [ ] Экспорт = слово «Экспорт» без города.
- [ ] Фильтр по статусу совпадает с доступом Свода.

## 5. UX «Заявка» (Passport + API)

### Сценарий (v3)
1. Открыть витрину биржи (уже отфильтрована: госостаток > 0 + статус).
2. Выбрать нужный лот.
3. Подать заявку.
4. Агент Биржи проверяет через СБ.
5. Если роль соответствует доступу → принято сразу; если ниже → ожидание подтверждения нужного уровня.
6. Статусы в UI отражают авто / «нужен Судья» / «нужен Страж» и т.д.

### API
- Один UX «заявка» (расширить `/exchange/needs` или `/exchange/applications` — выбрать при коде).
- Прямой `buy` не главный жест гражданина.
- Confirm endpoints должны знать **уровень лота**, не только `agent_sb` vs `live_guardian`.

### Passport (после ядра)
1. Витрина по статусу + госостаток.
2. Заявка с карточки лота.
3. Статусы: сразу / ждёт уровень N.
4. Экспорт без города.
5. Мэр — должность, не статус.

## 7. Открытые точки

1. Имя endpoint заявки.
2. Точная формула «уровень лота» из списка доступа (мин. роль в списке vs «самый высокий обязательный»).  
   Рабочая гипотеза для кода: **минимальная роль из «Доступ»**, которой достаточно, чтобы лот был «доступен» заявителю; для confirm — подтверждающий ≥ этой минимальной роли, и не ниже «потолка», если лот без нижних ролей (напр. только Сд, М → минимум Судья).
3. Может ли заявитель с ролью **ниже** доступа вообще подать заявку, или UI/API сразу режут? Канон допускает эскалацию («если ниже — нужно подтверждение») — при коде либо разрешить заявку+эскалацию, либо запретить подачу и оставить эскалацию только для confirm очереди. **Предпочтение уточнить у пользователя при реализации;** пока в спеке заложить оба исхода в changelog.
4. Как стыкуются `confirm_mode=agent_sb|live_guardian` со статусной иерархией: заменить полями `required_level` / `auto_confirmed` или маппить старые mode на новые правила.
5. Rates vs лоты в плоском Своде.
